# KODA: текущее состояние, принципы и направление

Обновлено: 10 августа 2026

## Что такое KODA

KODA — персональное PWA-приложение для планирования дня, целей, дневника и движения к собственной будущей версии. Это не просто todo-лист. Главная идея продукта: человек должен быстро понимать, что важно сегодня, что двигает его к целям, что уже сделано и где он сбился.

Приложение должно ощущаться как нативное мобильное приложение на iPhone и как полноценная desktop-программа на большом экране.

## Текущий стек

- Expo
- React Native
- React Native Web
- TypeScript
- Supabase
- Vercel API
- PWA / offline cache
- локальное состояние + синхронизация аккаунта между устройствами

Основная рабочая зона приложения находится в `src/features/koda`.

## Основные разделы

### KODA

Главная страница приложения по умолчанию. Это старт и завершение дня.

Сейчас здесь есть:

- запуск дня;
- завершение дня;
- KODA Score;
- классификация дня;
- цели и действия на сегодня;
- история завершённых дней;
- возможность удалить тестовые записи истории.

Принцип: до начала дня не показывать перегруженный список целей. Должна быть понятная точка входа — одна заметная кнопка `Начать`.

### Планнер

Раздел для конкретных дел по датам и времени.

Сейчас есть:

- режим дня;
- режим месяца;
- режим целей;
- задачи со временем;
- задачи без времени;
- подзадачи;
- редактирование;
- удаление с подтверждением;
- перенос задач между датами в месячном календаре;
- экспорт в iPhone Calendar через ICS.

Принцип: Планнер отвечает за конкретные дела. Действия из целей могут отображаться в Планнере, но редактировать их нужно внутри самой цели.

### Цели

Раздел для больших направлений.

Сейчас есть:

- глобальные цели;
- желаемый результат;
- срок;
- приоритет;
- этапы;
- разовые действия;
- регулярные действия;
- история выполнения регулярных действий;
- прогресс цели;
- действия на сегодня.

Принцип: не называть всё подзадачами. У цели есть отдельные сущности:

- цель;
- этап;
- разовое действие;
- регулярное действие.

Регулярные действия показывают дисциплину и темп, но сами по себе не должны доводить глобальную цель до 100%.

### Проекты

Раздел для бытовых или предметных проектов, которые не обязательно являются жизненными целями.

Примеры:

- мой авто;
- ремонт;
- переезд;
- документы;
- отпуск.

Сейчас есть:

- создание проекта;
- описание проекта;
- задачи внутри проекта;
- описание задачи;
- поле стоимости;
- статусы задач;
- прогресс проекта;
- архивирование проекта.

Принцип: проект — это контейнер дел вокруг конкретной темы. Например, `мой авто` может содержать `поменять лобовое стекло`, `покрасить крышу`, `купить резину`.

### Заметки

Раздел для любой информации, которую пользователь хочет сохранить и потом найти.

Сейчас есть:

- отдельная вкладка `Заметки`;
- список заметок;
- быстрый поиск по названию и plain-text содержимому;
- быстрое создание без предварительной формы;
- закрепление заметок;
- удаление через подтверждение;
- autosave;
- локальное сохранение через AsyncStorage;
- отдельная таблица Supabase `notes`;
- soft delete через `deleted_at`;
- structured JSON-документ;
- блоковый редактор первой версии.

Принцип: Заметки не являются Дневником, задачами или базой знаний. Это постоянное место для любой информации: данные машины, ссылки, рецепты, идеи, инструкции себе, номера договоров, списки и рабочие заметки.

Заметки не привязаны к конкретному дню, не влияют на KODA Score и могут редактироваться сколько угодно.

Редактор первой версии поддерживает:

- paragraph;
- H1 / H2 / H3;
- bullet list;
- numbered list;
- checklist;
- quote;
- code block;
- divider;
- toggle с дочерними блоками;
- простое inline-форматирование через компактный toolbar.

Архитектурно content хранится как JSON:

```ts
{
  type: 'doc',
  content: NoteBlock[]
}
```

Сознательно не реализовано сейчас:

- databases как в Notion;
- kanban;
- public pages;
- совместное редактирование;
- comments;
- version history UI;
- AI внутри заметок;
- web clipper;
- полноценный block-level conflict merge.

Если одна заметка меняется на двух устройствах одновременно, текущая безопасная стратегия — last-write-wins по `updatedAt`, без молчаливого восстановления удалённых заметок благодаря tombstone `deletedAt`.

### Дневник

Раздел для мыслей и состояния.

Сейчас есть:

- мысли дня;
- опциональный сон;
- опциональные метки;
- опциональное настроение;
- история записей;
- просмотр старой записи без редактирования;
- удаление записей с подтверждением.

Принцип: дневник не должен заставлять заполнять всё. Иногда пользователь хочет просто записать мысль.

### Прогресс

Раздел для общей аналитики.

Сейчас используется как место для:

- общего прогресса;
- выполненных задач;
- статистики целей;
- будущей аналитики по дням и регулярным действиям.

Принцип: desktop-версия должна быть аналитической страницей, а не растянутой мобильной колонкой.

### Профиль

Раздел аккаунта и настроек.

Сейчас есть:

- данные пользователя;
- смена пароля;
- уведомления;
- подписка на календарь iPhone;
- установка PWA на компьютер;
- цветовая схема приложения;
- виджетная лента;
- привычки / регулярные действия.

Принцип: настройки должны быть плотными строками, без больших декоративных блоков.

### Помощник

AI-раздел для помощи с задачами, целями и разбором дня.

Сейчас есть:

- чат;
- быстрые сценарии;
- контекст дня;
- поле ввода.

Принцип: на desktop это должен быть нормальный чат-интерфейс, где поле ввода закреплено снизу рабочей области.

## Дизайн-принципы

### Общий стиль

- тёмный фон;
- минимализм;
- компактность;
- тонкие границы;
- один главный акцент;
- без декоративного шума;
- без ощущения сайта внутри рамки;
- на мобильном — ощущение iPhone-приложения;
- на desktop — ощущение полноценной программы.

### Основная цветовая схема

Текущая основная схема — чёрно-оранжевая KODA.

Оранжевый акцент используется для:

- активного раздела;
- главного действия;
- прогресса;
- важных интерактивных состояний.

Оранжевый не должен расползаться везде. Если на экране всё оранжевое, акцент перестаёт работать.

### Альтернативная схема

Добавлена схема `Reference Dark`:

- тёмно-серые поверхности;
- синий акцент `#2f7df6`;
- светлый активный фон;
- приглушённые вторичные тексты.

Все элементы, которые используют акцент, должны брать его из theme tokens, а не из жёстких hex/rgba.

### Theme tokens

Цвета приложения должны идти через `src/features/koda/theme.ts`.

Нельзя добавлять новые жёсткие значения вроде:

```txt
#f26419
rgba(242, 100, 25, ...)
#ff6a1f
```

Если нужен новый вид акцента, нужно добавить токен:

- accent;
- accentSoft;
- accentFaint;
- accentGlow;
- accentBorder.

## Desktop layout

Desktop-версия не должна быть растянутым мобильным приложением.

Правила:

- слева navrail;
- рабочая область по центру;
- контент не растягивается бесконечно;
- ширина основных экранов ограничена;
- полезная правая колонка используется только там, где она нужна;
- большие экраны должны давать больше структуры, а не больше пустоты.

Ориентир:

- sidebar около 220 px;
- основной контейнер около 1028-1280 px;
- сетка 8/4 для страниц с правой колонкой;
- на мобильном всё схлопывается в одну колонку и нижнее меню.

## Mobile layout

Мобильная версия остаётся отдельным UX-ориентиром.

Правила:

- нижняя навигация;
- крупные touch targets;
- no horizontal scroll;
- input не должен вызывать zoom;
- формы не должны раздвигаться странными календарями;
- popup/bottom sheet вместо browser alert/confirm/prompt;
- учитывать safe area.

## Синхронизация и offline

KODA использует смешанную модель:

- данные сразу пишутся в локальное состояние;
- локально сохраняются в AsyncStorage;
- изменения ставятся в очередь синхронизации;
- при наличии аккаунта уходят в Supabase;
- при восстановлении сети приложение пытается досинхронизироваться.

Основные хранилища:

- `planner_events` — задачи Планнера и календарный экспорт;
- `journal_entries` — дневник;
- `user_app_state` — цели, привычки, KODA days, профиль, проекты;
- `profiles` — пользователь и простая авторизация.

Важно: пользователь не должен терять запись, цель или задачу из-за временного отсутствия интернета.

## iPhone Calendar / ICS

Планнер отдаёт задачи в iPhone Calendar через ICS.

Ограничение: скорость появления событий зависит от Apple Calendar. KODA может обновить ICS быстро, но iPhone сам решает, когда перечитать подписку.

Правило: календарь должен показывать именно запланированные дела, а не тестовые или статичные шаблоны.

## Уведомления

Push-уведомления подключены через профиль и backend.

Текущее тестовое время может меняться миграциями и настройками. Важно помнить: PWA push на iPhone зависит от разрешений, установки приложения на экран и системных ограничений Apple.

## PWA

KODA должна устанавливаться:

- на iPhone как PWA;
- на desktop как веб-приложение через Chrome/Edge.

Проверять:

- `manifest`;
- service worker;
- иконки;
- offline loading;
- корректное обновление bundle после deploy.

## Ownership сущностей

KODA держится на разделении владельцев данных.

### Планнер

Планнер владеет самостоятельными пользовательскими делами: дата, время, название, подзадачи и статус выполнения.

У таких дел `sourceType = planner`. Это обычные задачи, которые можно редактировать, удалять, переносить и экспортировать в iPhone Calendar.

### Цели

Цели владеют этапами, разовыми действиями и регулярными действиями. Планнер может показывать актуальные действия целей, но не должен превращать их в независимые копии.

Редактирование целевых действий должно происходить внутри цели.

### Проекты

Проекты владеют проектными задачами. Если у проектной задачи указана дата планирования, она появляется в Планнере как проекция:

- `sourceType = project`;
- `sourceId = id задачи проекта`;
- `ownerId = id проекта`.

Такую задачу можно отметить выполненной или перенести на другую дату из Планнера. Это меняет исходную задачу проекта. Редактирование текста, стоимости и описания остаётся в разделе `Проекты`.

### Recurring / Habits

Текущий раздел привычек и регулярные действия целей концептуально близки. Долгосрочное направление: привести их к единой модели recurring action, но не ломать текущий UX до появления понятной миграции.

## Sync-правила

Для новых сущностей нужно придерживаться local-first модели:

- `id` создаётся сразу на клиенте;
- `updatedAt` меняется при каждом изменении;
- удаление там, где возможны конфликты синка, лучше делать через `deletedAt`;
- UI скрывает `deletedAt`, но tombstone остаётся в состоянии до безопасной очистки;
- merge должен сравнивать свежесть, а не просто порядок массивов.

Проектные задачи уже используют `deletedAt`, чтобы удалённые задачи не воскресали после синхронизации разных устройств.

## KODA Score

Формула счёта должна жить централизованно в `src/features/koda/kodaScore.ts`.

Текущая версия:

- цели: 90 баллов;
- планнер: 10 баллов;
- регулярность отдельно пока не добавляет баллы.

Это зафиксировано в `KODA_SCORE_WEIGHTS`. Если формула меняется, нужно менять её там же и сохранять weights в snapshot завершённого дня.

## Текущее ограничение архитектуры

Часть данных всё ещё хранится в `user_app_state` JSON:

- цели;
- привычки;
- KODA days;
- профиль;
- проекты.

Это рабочий компромисс для текущей версии. Долгосрочно крупные сущности нужно выносить в отдельные таблицы:

- `projects`;
- `project_tasks`;
- `recurring_actions`;
- `recurring_action_logs`;
- `koda_days`;
- `completions`.

Переход должен идти через compatibility layer, чтобы не потерять данные пользователей.

## Текущее направление продукта

KODA должна развиваться в сторону системы дня:

1. Сначала человек открывает KODA.
2. Запускает день.
3. Видит только важное.
4. Делает задачи в Планнере.
5. Двигает цели регулярными и разовыми действиями.
6. Записывает мысли в Дневник без давления.
7. Вечером фиксирует итог.
8. Прогресс собирается без лишней ручной бухгалтерии.

## Критерии качества

Перед тем как считать крупную правку готовой:

- мобильная версия работает;
- desktop-версия не выглядит как растянутый телефон;
- нет горизонтального скролла;

# Desktop layout architecture

All nine KODA desktop sections follow the Planner-derived application composition:

```text
GlobalNav + PageArea(MainColumn + RightColumn)
```

- **GlobalNav** remains stable at 210px (72px collapsed), full height, with the existing order, icons, and selected states.
- **PageArea** uses the available desktop width with 28px horizontal padding and a 1360px maximum.
- **MainColumn** receives the remaining PageArea width and is always the visually dominant current-work region.
- **RightColumn** is normally 330px with a 24px gap and contains useful section navigation, history, controls, or context. It is a layout region, not an optional modal inspector or giant card.

Planner remains the reference: planner work stays in MainColumn and quick actions, focus, upcoming tasks, and progress stay in RightColumn. Projects, Goals, Notes, and Journal use the entity rule: the selected object is in MainColumn and object navigation/history is in RightColumn. KODA Day, Progress, Profile, and Assistant use the functional rule: current work is central and existing context/navigation occupies the right region.

Desktop Notes keeps the selected editor in MainColumn and its searchable note navigation plus visible create action in RightColumn. Mobile keeps its existing fullscreen list/editor transition and bottom navigation.

GlobalNav remains fixed while the page content scrolls independently. Mobile retains its separate composition and never renders the desktop three-column system.

### KODA Day: source of truth and cross-device lifecycle

For authenticated accounts, `public.koda_days` is the canonical source of truth for KODA Day. A day is uniquely identified by `(user_id, local_date)`; `local_date` is produced by the existing local-calendar strategy (`todayDateKey`) and the originating IANA timezone is stored on the entity.

Start and Finish are local-first: React state and scoped AsyncStorage update immediately, then the `kodaDays` sync domain is queued and flushed to Supabase with an upsert on `(user_id, local_date)`. The server row ID is deterministic for that user and date, so retries and simultaneous devices cannot create duplicate days.

On cold start, browser focus, visibility resume, and the existing periodic foreground pull, the app fetches `koda_days` and merges local and remote entities by `localDate` and `updatedAt`. A newer ACTIVE or COMPLETED entity wins over a stale device. Pending monolithic `user_app_state` changes never suppress this fetch. Offline Start remains ACTIVE locally; reconnect retries the queued upsert. The legacy `user_app_state.koda_days` JSON remains a backward-compatible migration fallback, but it is not authoritative.
